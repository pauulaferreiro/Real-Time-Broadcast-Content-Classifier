# Real-Time-Broadcast-Content-Classifier

This project implements a system that captures live television signals, extracts their Event Information Table (EIT) metadata and video frames, and uses a multimodal large language model (Ministral-3-3B) to classify broadcast programs in real time. It also includes a monitoring system to measure energy consumption during execution.

System Architecture and Workflow

The system is divided into three independent processes. The following diagram illustrates the implemented architecture and processing workflow:



Color legend:

Blue: Input source (UDP/MPEG-TS stream).

Orange: Data extraction, DVB table reassembly, and model inference processes.

Green: Flow-control and filtering stages (broadcast detection, Laplacian variance thresholds, and SSIM).

Purple: System outputs and generated files.

.xml files: Contain raw EIT metadata extracted for each event, including the program title, extended description, broadcast schedule, and parental rating.

.jpg files: Contain video frames extracted from the original stream using FFmpeg.

.csv files: Three separate CSV files are generated:

dataset_tiempo_real.csv: A raw acquisition log containing information about each detected event, including its schedule, duration, and original broadcaster-assigned category.

reporte_final_predicciones.csv: The final classification report generated by the system. It includes the number of analyzed frames, the MLLM's final prediction, and the filtering threshold values used during execution.

system_monitor.csv: A time series containing energy consumption, power measurements, hardware utilization, and resource usage associated with the system and its subprocesses.

.json files: Store detailed event-level inference results, including frame-by-frame predictions, confidence percentages, decision explanations (reasoning), and hardware performance metrics.

.txt files: The system_monitor_report.txt file provides a summary of operational costs, including total session cost, hourly/daily/monthly estimates, and average and peak hardware utilization. The electricity price (€/kWh) can be configured.

White/Black: Routine operations and processing loops.

Prerequisites

Python 3.10 or later.

FFmpeg installed on the operating system.

Python dependencies:

pip install torch torchvision transformers pillow opencv-python scikit-image psutil pynvml pyRAPL

On Intel-based systems, read permissions for the RAPL power measurement interface must be enabled by running:

sudo chmod -R a+r /sys/class/powercap/intel-rapl

Running the System (Three Terminals)

The system follows a decoupled architecture. Three independent processes must be launched in separate terminal sessions.

Step 1. Terminal 1: Start the Controller

Open a terminal and run:

python controller.py

The controller runs continuously, waiting for new video frames and metadata generated by the receiver.

It is recommended to start the controller before initiating signal reception so that it is ready to process incoming data.

Additional configuration options are available for filtering parameters and directory organization.

The filtering thresholds can be adjusted using the following arguments:

--ssim-threshold: Structural Similarity Index (SSIM) threshold. Measures the similarity between the current frame and the previously accepted reference frame. Default: 0.6.

--laplacian-min: Minimum Laplacian variance threshold. Filters out frames lacking useful structural information, such as black screens or images dominated by irrelevant visual elements (e.g., large logos). Default: 70.

--laplacian-max: Maximum Laplacian variance threshold. Filters out frames with excessive high-frequency content, potentially associated with rapidly changing scenes or visually degraded frames. Default: 2300.

Step 2. Terminal 2: Start Signal Acquisition

Open a second terminal window to receive the UDP stream.

When the system detects an active broadcast event, it begins extracting metadata and video frames using FFmpeg.

The UDP address, port, and total capture duration (in seconds) must be specified:

python receiver_signal.py --record-ip udp://X.X.X.X:YYYY --record-seconds 3600

Additional optional settings allow customization of the frame extraction strategy, sampling interval, and output directory.

Step 3. Terminal 3: Start the System-Wide Cost Monitor

Open a third terminal window and start the monitoring process:

python system_monitor.py

This module independently monitors CPU energy consumption using pyRAPL, GPU energy consumption using NVML, and the resource usage of project-related processes, including FFmpeg, the controller, and the inference pipeline.

Output Structure

As the system runs, it automatically creates an organized directory structure.

The system generates three separate CSV files, each serving a specific purpose.

1. Acquisition Outputs

RESULTADOS_MUX/frames_seleccionados/: Extracted .jpg frames, organized by television service and event.

RESULTADOS_MUX/eit_extraidas/: Program guide metadata extracted from EIT tables and stored in XML format.

RESULTADOS_MUX/dataset_tiempo_real.csv: Raw acquisition log containing detected broadcast events, timestamps, and the original DVB content category provided by the broadcaster.

2. Controller Outputs

RESULTADOS_MUX/reporte_final_predicciones.csv: Final classification report containing the program-level category selected through the MLLM-based classification process, the number of analyzed frames, and the filtering thresholds used during execution.

resultados_frames/: JSON files containing detailed frame-by-frame classification information, including MLLM predictions, confidence levels, decision explanations, and hardware consumption metrics.

logs/: Debugging logs (video_classifier.log) and individual inference latency records (latency.log).

3. System-Wide Monitoring Outputs

logs/system_monitor.csv: Continuous monitoring records containing energy consumption (J), power measurements (W), and hardware utilization percentages (%) associated with the project environment.

logs/system_monitor_report.txt: Final text report summarizing average power consumption, peak hardware usage, total session cost (€), and longer-term cost projections based on the configured electricity price.
